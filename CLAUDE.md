## Project

« Challenger, par Aceep&Kyle » — self-service book-challenge platform (French UI, code in English). Any Discord account may sign in and open its own challenge for its community; players join by invitation or with `/challenger rejoindre` on the challenge's Discord server. Teams earn points by reading (per page), filling bingo grids and completing quests; each team also plays a shared branching "you're the hero" story voted on Discord/in-app with game effects. Full spec and phasing: `~/.claude/plans/we-will-start-from-drifting-dijkstra.md`.

Do not use the `dsi:*` skills/agents here (personal project, not a Davidson internal repo).

## Stack notes (Next.js 16 — conventions differ from older training data)

- Read `node_modules/next/dist/docs/01-app/02-guides/upgrading/version-16.md` before touching framework-level code. Key points already applied:
  - `proxy.ts` replaces `middleware.ts` (Node runtime only). It does an optimistic cookie check only.
  - `params`, `searchParams`, `cookies()`, `headers()` are Promises — always `await`.
  - Global helper types `PageProps<'/route'>`, `LayoutProps<'/route'>`, `RouteContext<'/route'>` (generated by `next typegen`/`next dev`).
  - Use `after()` from `next/server` for fire-and-forget side effects (Discord posts).
  - Cache Components (`cacheComponents`) are NOT enabled; pages are dynamic by default when they read the session.
- Prisma 7: config in `prisma.config.ts` (loads `.env` via dotenv), client uses the Neon driver adapter (`lib/db.ts`). No `url` in `schema.prisma`.
- Auth.js v5 (`auth.ts`): Discord-only OAuth, JWT sessions. **Any Discord account may sign in** — the platform is open, and invitations only decide which challenges are joined, never who may connect. The JWT carries only `id`, `discordId` and `isSuperAdmin` — **never a role**. `events.linkAccount` (first login) and `events.signIn` (every login) both call `consumePendingInvites`, which is idempotent: an invitation created after the first connection takes effect on the next one.

## Rulebook

`SPEC-challenge-lecture.md` (repo root) is the source of truth for game rules; decisions on its §12 open points are recorded in the plan file ("Spec alignment"). Key implemented rules: points = pages/10 (halved under 150 p.), commercial rounding to 0,1, stored on `Book.points` and as `Decimal(8,1)` in the ledger (read with `num()` from `lib/services/points.ts`, display with `fmtPoints`); effective type `ROMAN|GRAPHIQUE` (<150 p. ⇒ graphique); quests are team-level and numbered; bingo is an ordered series of grids (`TeamGrid` = a team's active grid); readings are soft-deleted (`deletedAt`) — always filter `deletedAt: null`; Sunday 19–21 h Europe/Paris verification window refuses non-admin writes (`assertWritable`).

Time-driven work (window announcements, Sunday 20 h leaderboard post with catch-up, vote expiry, tie cascade, dormant reminders) lives in `lib/services/tick.ts` (`runTick`, idempotent via `BotEvent`). It is triggered by `/api/cron/tick` (Vercel crons in `vercel.json` — the Hobby plan only allows daily, imprecise crons) and on activity (`tickOnActivity`, throttled, from the player layout and the Discord endpoint). For minute-precision, point an external scheduler at `GET /api/cron/tick?secret=$CRON_SECRET` hourly.

## Multi-tenant

Several challenges coexist, isolated: each has its own organisers, teams, Discord server and rulebook. `Challenge` is the tenant root.

- A role only exists **inside** a challenge: `ChallengeMember { challengeId, userId, role: ORGANIZER | PLAYER }`. There is no global `User.role`; the only platform-wide flag is `User.isSuperAdmin` (organiser of every edition, sees every challenge in the editions list).
- `TeamMember` is keyed `(userId, challengeId)`: at most one team per person **per edition**, so the same person plays several challenges.
- What may be the current challenge, and what one may switch to, is one list: `listSwitchableChallenges(userId)` (memberships + every edition for a super-admin, who organises them all). It feeds both `currentMembershipFor` and the edition switcher, so the two can never disagree.
- The "current challenge" of a web request: the `challenge` cookie when that edition is open to the person, otherwise their ACTIVE edition, otherwise the latest one (`lib/tenancy/select.ts`, pure and tested; I/O in `lib/services/membership.ts`).
- The cookie is written **only** through `lib/tenancy/cookie.ts` (`setCurrentChallengeCookie` / `clearCurrentChallengeCookie`): `switchChallengeAction` (`app/(player)/help/actions.ts`, reachable from Aide › Édition, the admin rail and the editions table of Admin › Défi) and `createChallengeAction` (`/new`, which lands on the edition it just created). It lasts a year and is deleted on sign-out. Landing after a switch is capped by `switchLanding`: the admin desk only for an ORGANIZER of the target. The current edition is spelled out permanently in both shells (`EditionBar`, the « Plus » sheet, the rail block) — its colour paints `--edition`.
- **Getting in.** Two creation paths, one service each, both landing on a DRAFT edition whose author is its first ORGANIZER: the web form `/new` → `createChallengeAction` (`app/(player)/new/actions.ts`), and `/challenger creer` on Discord → `createChallengeFromGuild` (`lib/services/challenger.ts`), reserved to « Gérer le serveur » (`hasManageGuild`) and refused when the server already runs a non-FINISHED challenge. Two joining paths: an `Invite` (consumed at the next login) or `/challenger rejoindre` → `joinChallengeFromGuild`. A Discord id with no account yet is never pre-created as a `User` — an `Invite` (ORGANIZER or PLAYER) waits for the first OAuth. Defaults for a new edition are pure: `lib/tenancy/new-challenge.ts`.
- **Two command sets.** `SLASH_COMMANDS` (`lib/discord/commands.ts`) are registered **per guild** by the bootstrap; `GLOBAL_COMMANDS` (`lib/discord/challenger.ts`, just `/challenger`) are registered **application-wide** so they answer on a server that has no challenge yet — `npm run discord:register -- --global`, propagation up to an hour. The two lists stay disjoint, or the command shows up twice.
- A Discord interaction resolves its tenant from `guild_id` (`resolveDiscordActor`): the ACTIVE challenge of that server, else its latest edition. A community reuses its server every edition, so `discordGuildId` is indexed but not unique — the invariant "at most one ACTIVE challenge per guild" is enforced in `upsertChallenge`.
- Every service function takes the challenge it acts in; a team, an invitation, a question or a rival from another edition is refused.

## Architecture rules

- **Authorization lives in `lib/dal.ts`**, called inside every page, Server Action and Route Handler. Never rely on layouts or the proxy for security.
  - `requireUser()` — session only.
  - `getCurrentPlayer()` → `{ user, challenge, role, team }`, all null-able but `user`.
  - `requireOrganizer(challengeId?)` → `{ user, challenge }`; redirects to `/home` unless the person is ORGANIZER of that challenge (a super-admin always passes). Defaults to the current challenge.
- **Scores are an append-only ledger** (`PointEvent`). Never store a mutable team total; team score = sum of `amount` within the challenge window. Multipliers (`Modifier`) are resolved when the event is written (`baseAmount`, `multiplier`, `amount` all stored). Undo = negative event.
- Pure game logic (points, bingo lines, vote resolution, story effects) goes in `lib/scoring/*` and `lib/story/*` with no I/O, and is unit-tested. Server Actions and Discord slash commands must call the same service functions (`lib/services/*`) — no duplicated business logic.
- Mobile-first UI (Tailwind 4), French copy with proper typography (apostrophes, accents).
